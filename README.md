# AI Sales Demo Suite — AI-продавец для Avito

Демонстрационный продукт по ТЗ «AI-ассистент для общения, квалификации и доведения
клиентов из Avito до целевого действия». Одно приложение, одна база, девять
связанных разделов: сообщение, написанное в Live Sales, меняет тот же лид, который
рисует CRM и считает Analytics.

Сквозной путь работает целиком:

```
клиент пишет → извлечение параметров → скоринг квалификации → правила передачи →
подбор из наличия → response guard → CRM-мутации → задача менеджеру →
встреча и напоминания → follow-up по расписанию → аналитика и самоанализ
```

---

## 1. Что это

| Раздел | Что показывает |
|---|---|
| **Live Sales** | Диалоги, чат клиент ↔ AI, панель Live Intelligence (квалификация, температура, сигналы, next best action, handoff, задача с SLA) |
| **CRM** | Kanban-воронка лидов, карточка сделки, задачи с дедлайном 5 минут, менеджеры и смены |
| **Inventory** | 48 позиций, остатки, «пригодность под задачу», источник наличия для AI |
| **Follow-ups** | Планировщик повторных касаний и напоминаний о встрече, с ускорением демо-часов |
| **Analytics** | Воронка, конверсии, ежедневный отчёт в формате §39, источники, KPI |
| **AI Insights** | Самоанализ: где теряются клиенты, где handoff был поздним, что даёт контакт |
| **Control Center** | Правила квалификации, передачи, follow-up, встреч, стиля и продаж + журнал изменений |
| **Knowledge Base** | 4 независимые ветки БЗ с версионированием и откатом |
| **Logs / Debug** | Полная трассировка каждого ответа AI |

### Ключевая архитектурная идея

**Backend решает, *что* сказать. Модель решает только, *как* это сформулировать.**

Бэкенд считает состояние квалификации, проверяет наличие в учётной системе,
применяет правила передачи и формирует «план ответа». Модель получает план и
список **разрешённых** товаров с точными характеристиками и ценами. Поэтому:

* AI физически не может придумать наличие, цену или характеристику;
* поведение одинаково с реальной моделью и без неё;
* демонстрация воспроизводима.

Перед отправкой каждый ответ проходит **Response Guard** — 12 проверок из §45
(товар существует, есть в наличии, цена актуальна и не выше объявления, нет
запрещённых утверждений, не переспрашивает закрытое, менеджер не перехватил чат,
товар подходит задаче, нет неподтверждённых фактов…). Это backend-валидация, а не
инструкция в промпте: модель, проигнорировавшая системный промпт, всё равно не
пройдёт гейт.

## 2. Architecture

```
frontend (React 18 + TypeScript + Vite + Tailwind + Recharts)
   │  nginx: отдаёт SPA, проксирует /api → backend
   ▼
backend (FastAPI + SQLAlchemy 2 + Pydantic v2)
   ├── core/extractor.py      детерминированный разбор русской переписки
   ├── core/qualification.py  состояние + настраиваемая формула процента
   ├── core/product_expert.py подбор, ранжирование, честная оценка соответствия
   ├── core/handoff.py        правила передачи + температура лида
   ├── core/meeting.py        лестница закрытых вопросов из §10
   ├── core/followup.py       тайминги §12/§13
   ├── core/guard.py          12 проверок перед отправкой
   ├── core/crm.py            этап воронки, направление, качество заявки
   ├── core/kb.py             модульная БЗ с версиями
   ├── core/pipeline.py       оркестратор хода диалога
   ├── llm/                   LLMProvider: anthropic | openai-compatible | demo
   ├── adapters/              AvitoAdapter / CRMAdapter / InventoryAdapter / MediaAdapter
   ├── clock.py               виртуальные демо-часы (×1 … ×600)
   └── scheduler.py           фоновый поток: follow-up, напоминания, SLA
   ▼
postgres (в docker-compose; наружу не публикуется)
```

## 3. Local start

Нужен только Docker.

```bash
git clone https://github.com/wertyuc/ai-sales-demo.git
```
```bash
cd ai-sales-demo && ./deploy.sh
```

Скрипт создаст `.env` со свежими секретами, соберёт образы, поднимет стек и
напечатает URL, логин и пароль.

### Без Docker (только backend)

```bash
cd ai-sales-demo/backend
python -m venv .venv && ./.venv/bin/pip install -r requirements-dev.txt
./.venv/bin/uvicorn app.main:app --reload
```

По умолчанию используется SQLite и детерминированный demo-провайдер — работает
без единой переменной окружения. Фронтенд в режиме разработки:

```bash
cd ai-sales-demo/frontend
npm install && npm run dev      # http://localhost:5173, /api проксируется на :8000
```

## 4. Production deployment

```bash
./deploy.sh --port 8080     # собрать и запустить
./deploy.sh --logs          # логи
./deploy.sh --restart       # перезапуск
./deploy.sh --reset         # стереть БД и пересоздать демо-данные
./deploy.sh --down          # остановить
```

Наружу публикуется **только** контейнер `web` (nginx). PostgreSQL и backend живут
во внутренней docker-сети и не имеют опубликованных портов. У всех сервисов —
`restart: unless-stopped`, healthcheck и именованный том для данных Postgres.

Обновление:

```bash
git pull && ./deploy.sh
```

| `LLM_PROVIDER` | `auto` | `auto` \| `anthropic` \| `openai` \| `demo` |
| `ANTHROPIC_API_KEY` | пусто | ключ Anthropic |
| `ANTHROPIC_MODEL` | `claude-opus-5` | модель |
| `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL` | — | любой OpenAI-совместимый endpoint |
| `SEED_ON_STARTUP` | `true` | создать демо-данные при первом запуске |

| `DEMO_SPEED` | `60` | виртуальных минут в реальной секунде |

Секреты хранятся только в `.env`, который в `.gitignore`. В интерфейс и логи
ключи не выводятся.

## 7. Demo scenarios — что показать заказчику

В Live Sales нажмите **Сценарий**. Каждый сценарий проигрывается через реальный
pipeline: квалификация, подбор и правила отрабатывают по-настоящему.

| Сценарий | Что демонстрирует |
|---|---|
| **Горячий лид из Москвы** | Клиент сразу даёт бюджет, город и срок → квалификация закрывается за один шаг, лид HOT, сразу 2-3 варианта из наличия |
| **Несоответствие товара** | Просит ультрабук под Cyberpunk → AI **не соглашается ради продажи**, объясняет причину и предлагает то, что реально потянет игру |
| **Товара нет в наличии** | Запрошена позиция с остатком 0 → AI прямо говорит об отсутствии, не выдумывает причину, предлагает аналоги |
| **Регион + доставка** | Казань и 4 закрытых пункта → срабатывает правило «регион + 4», направление «Доставка регион» |
| **Клиент просит позвонить** | Немедленная передача менеджеру, задача с дедлайном 5 минут |
| **Подозрение на AI** | «Мне кажется, я с роботом разговариваю» → CRITICAL HANDOFF, AI замолкает |
| **Негатив клиента** | Фиксация негатива, передача менеджеру, лид помечен как негативный |
| **Клиент пропал** | Планировщик ставит касание через 15 минут — ускорьте часы, чтобы увидеть отправку |

### Сценарий показа за 10 минут

1. **Live Sales** → «Сценарий» → **Горячий лид из Москвы**.
   Смотрим правую панель: параметры закрываются, Qualification растёт, лид HOT,
   появляется **HUMAN HANDOFF REQUIRED** с причиной и назначенным менеджером.
2. Пишем от имени клиента «**Куда приехать?**» → AI шлёт адрес и задаёт закрытый
   вопрос. Отвечаем «**Да, сегодня удобно**» → «**Вторая половина, в 18:00**» →
   встреча зафиксирована, поставлены напоминания.
3. **CRM** — тот же клиент уже в нужной колонке; открываем карточку: бюджет,
   география, задачи, выбранные модели, менеджер, задача с обратным отсчётом.
4. **Сценарий → Несоответствие товара** — AI отказывается продавать неподходящее.
5. **Inventory** — ставим остаток 0 у модели, спрашиваем про неё в чате: AI
   отказывается подтверждать наличие.
6. **Follow-ups** — переключаем скорость на **×600** в шапке: касание «через 15
   минут» уходит на глазах, следующее переносится в окно 12:30–14:30.
7. **Analytics** — воронка, конверсии, ежедневный отчёт в формате из ТЗ.
8. **Control Center** — меняем «Порог автопередачи» с 80 на 50, сохраняем,
   пишем новое сообщение — правило срабатывает раньше. Изменение видно в
   журнале со старым и новым значением.
9. **Logs / Debug** — раскрываем последний ответ: извлечённые параметры, правила,
   фрагменты БЗ, снимок наличия, проверка цены, 12 safety-проверок, мутации CRM.

## 8. Database

```bash
./deploy.sh --reset                                  # пересоздать всё
docker compose exec db psql -U aisales -d aisales    # консоль psql
docker compose exec -T db pg_dump -U aisales aisales > backup.sql   # бэкап
cat backup.sql | docker compose exec -T db psql -U aisales -d aisales   # restore
```

Схема создаётся автоматически при старте (`Base.metadata.create_all`), демо-данные
— идемпотентным сидом. Десять демонстрационных диалогов не «нарисованы»: они
проигрываются через реальный pipeline с отмотанными назад часами, поэтому их
квалификация, этапы CRM, события и логи настоящие — и аналитика считается по ним,
а не по выдуманным цифрам.

## 10. LLM — как подключить реальную модель

Демо работает без ключа: `DemoProvider` рендерит план ответа детерминированно.
Чтобы подключить настоящую модель, достаточно одной переменной в `.env`:

```bash
ANTHROPIC_API_KEY=sk-ant-...
# необязательно:
ANTHROPIC_MODEL=claude-opus-5
```

```bash
./deploy.sh --restart
```

Любой OpenAI-совместимый endpoint (vLLM, Ollama, OpenRouter, российский шлюз):

```bash
LLM_PROVIDER=openai
OPENAI_API_KEY=...
OPENAI_BASE_URL=https://your-gateway/v1
OPENAI_MODEL=your-model
```

Провайдер обёрнут `FallbackProvider`: при сетевой ошибке ответ формирует
детерминированный провайдер, диалог не ломается, факт деградации виден в
Logs / Debug. Новый провайдер — это один класс с методом `generate` в `app/llm/`.

Бизнес-логика общается только с четырьмя интерфейсами (`app/adapters/base.py`).
Замена реализации не затрагивает `core/`:

| Интерфейс | Сейчас | Подключить |
|---|---|---|

## 12. Что сейчас mock, а что работает по-настоящему

**Работает по-настоящему:** извлечение параметров из русской переписки, скоринг с
настраиваемыми весами, подбор и ранжирование по наличию, честная оценка
соответствия задаче, все правила передачи менеджеру, round-robin по сменам,
задачи с дедлайном, лестница записи на встречу, планировщик follow-up и
напоминаний на виртуальных часах, response guard, CRM-воронка, аналитика,
самоанализ, редактор правил с журналом изменений, БЗ с версиями и откатом,
логирование каждого хода, авторизация.

**Mock:** транспорт Avito (чат внутри приложения), Bitrix24 (собственная demo-CRM),
МойСклад (таблица `products`), Яндекс.Диск (медиа не выгружаются, фиксируется
задача менеджеру). LLM по умолчанию — детерминированный провайдер.

**Для production потребуется:** ключи Avito Messenger API и подтверждение, что
отдаётся статус прочтения (от него зависит правило 15 минут); вебхук Bitrix24 с
правами на лиды/сделки/задачи; ключ связи карточки МойСклад с объявлением Avito;
сервисный аккаунт Яндекс.Диска; решение по 152-ФЗ о допустимости зарубежной LLM;
график смен менеджеров; формальные определения «качественной» и «некачественной»
заявки. Полный список — раздел 48 исходного ТЗ.

## 13. Tests

```bash
cd backend && ./.venv/bin/pytest -q
```

63 теста в трёх файлах:

* `test_extraction.py` — разбор переписки (включая ловушки: «ра**бот**ы» ≠ бот,
  «монтаж **видео**» ≠ запрос видео, «RTX 4060» ≠ бюджет) и формула квалификации;
* `test_pipeline.py` — сквозной happy path, запрет предлагать отсутствующий
  товар, формат цены «ОТ», отказ от неподходящей модели, все правила handoff,
  перехват чата человеком, лестница встречи, влияние Control Center;
* `test_scheduler.py` — лестница касаний на виртуальных часах: прочитал и молчит
  → 15 минут; не читает → перенос и остановка после лимита; отмена при ответе
  клиента и при перехвате; приоритетные окна; напоминания о встрече; просрочка SLA;
* `test_api.py` — HTTP-уровень: авторизация, жизненный цикл диалога с проверкой
  отсутствия «сирот» после удаления, аудит Control Center, версии БЗ.

Внешние ключи в SQLite включены (`PRAGMA foreign_keys=ON`), поэтому локальные
тесты ловят нарушения целостности так же, как их поймал бы Postgres.
